Documentazione Valutatore Immobiliare – Architettura & Flussi

Panoramica completa di frontend, backend, motore OMI ufficiale + fallback sintetico, dashboard admin e runbook operativo. I diagrammi sono ricostruiti a partire dal codice reale.

React + Vite Express + SQLite OMI ufficiale + sintetico Docker multi-container
⚙ Architettura generale
Frontend React, backend Express, DB utenti e DB OMI ufficiale
Vista sintetica

Frontend

  • SPA React 18 con Vite (entry in src/main.jsx, core in src/App.jsx).
  • Stili globali in src/index.css (Tailwind + classi custom, mappe, accessibilità).
  • Wizard valutazione passo-passo + landing di provincia + blog.
  • Dashboard admin integrata nella stessa SPA (tab overview, contatti, analytics, GDPR).

Backend

  • Express 4, API definite in server/index.js.
  • SQLite tramite better-sqlite3 per:
    • leads (users_leads, lead_media, lead_ai_analysis)
    • analytics landing di provincia (province_analytics_events)
  • DB OMI ufficiale dedicato in data/omi_official.sqlite gestito da OmiOfficialRepository.

Deploy

  • Docker multi-container (backend Node + frontend statico Nginx).
  • Reverse proxy frontend → backend via path /api.
  • Volumi per persistenza DB e file upload.

Passi di dettaglio

  • Ricerca indirizzo: searchAddresses() usa database locale + Nominatim + Photon con deduplica intelligente.
  • Enrich CAP: enrichAddressWithCAP() fa reverse geocoding e applica override CAP per comuni critici.
  • Pre-OMI sintetico: getOmiValues(cap) garantisce sempre un set di valori (anche stimati) per evitare errori.
  • Valutazione principale: calculateEnhancedValuation() chiama il backend; il backend usa prima OMI ufficiale e poi OMI sintetico.
  • Media upload: i file sono caricati in un archivio in memoria lato server per essere analizzati in modo semplice (nessuna AI esterna, solo regole sul numero di foto/planimetria).

Note operative

  • Se il DB OMI ufficiale non è disponibile, il sistema passa in modalità sintetica senza bloccare l’utente.
  • La provenienza dei dati è indicata da source e metadati.reliability nella risposta.
  • La logica media/“AI analyze” non modifica la fonte dei dati, ma solo un delta sul prezzo finale.

Sintesi file principali & punti critici
Per ogni area: cosa fa e dove prestare attenzione.

Backend – server/index.js

  • Setup: inizializza Express, CORS condizionale per path /api, JWT admin e rate limiter.
  • Login admin: /api/admin/login-step1 e /login-step2 gestiscono password e TOTP.
  • Leads: /api/leads gestisce upload (planimetria + foto) e inserimento nel DB.
  • Analytics: /api/analytics/province/pageview salva eventi e gli endpoint admin li aggregano.
  • Valutazione: /api/valuation/enhanced-omi è l’endpoint principale che usa OMI ufficiale con fallback sintetico.
  • Media “AI analyze”: /api/valuation/ai-analyze calcola un punteggio semplice basato su file caricati.

Punti critici server/index.js

  • CORS: è consentito solo per origin in ADMIN_ALLOWED_ORIGINS e per qualsiasi localhost. Se non configurato correttamente, il login admin fallisce lato browser.
  • OMI ufficiale: se il DB ufficiale non è disponibile o OMI_DB_PATH è errato, il repository non si inizializza e si passa sempre a fallback sintetico.
  • Modalità strict: con OFFICIAL_MODE_STRICT=1, se non c’è dato ufficiale o la tipologia non è mappata viene restituito errore 4xx/5xx e non viene usato fallback sintetico.
  • Login admin: l’uso di ADMIN_PASS in chiaro è comodo in sviluppo ma non raccomandato in produzione.

Backend – server/db.js

  • Schema: definisce tabelle per leads, media, analisi AI e eventi analytics province.
  • Funzioni principali: insertLead, insertMediaRecords, insertAiAnalysis, getAdminLeads, getProvinceAnalyticsSummary, getProvinceAnalyticsTimeseries.

Punti critici db.js

  • Nessun indice esplicito: con molti dati, query per lead e analytics potrebbero rallentare.
  • Dati personali in chiaro: nessuna cifratura a riposo (dipende dai requisiti di compliance del titolare).

Backend – OmiOfficialRepository.js & mapping tipologie

  • OmiOfficialRepository apre omi_official.sqlite in sola lettura, prepara statement per:
    • trovare i comuni a partire dal CAP;
    • estrarre l’ultimo semestre attivo;
    • calcolare il range MIN/MAX €/mq per comune e tipologia.
  • mapUiCategoryToOmi traduce le categorie dell’interfaccia nelle descrizioni OMI.

Punti critici

  • Se non si aggiorna la mappa delle tipologie, nuove categorie UI non saranno coperte in modalità strict.

Frontend – App.jsx

  • Gestisce:
    • wizard di valutazione (indirizzo → proprietà → risultato);
    • popup contatto e invio lead;
    • routing interno (privacy, pre, landing di provincia, blog, blog-detail);
    • admin login e dashboard staff;
    • tracking analytics landing di provincia.
  • Definisce funzioni chiave: handleAddressSelect, calculateEnhancedValuation, calculateTraditionalValuation, applyMediaDeltaToValuation, goBack, restart.

Punti critici App.jsx

  • “God component”: molto stato e molta logica in un solo file; refactoring consigliato per scalabilità e testabilità.
  • Coesistenza di due sistemi di valutazione (enhanced-omi backend vs calcoli locali), anche se oggi viene usato principalmente il primo.

Struttura dettagliata di App.jsx

Per capire a fondo src/App.jsx è utile considerare, per ciascun blocco, il ruolo generale, le sezioni principali, le variabili di stato importanti, cosa fa ogni funzione rilevante e come si collega agli altri file.

Ruolo

  • Controlla gran parte dell’app:
    • flusso del wizard di valutazione;
    • landing (home, pre, landing di provincia, blog, pagine legali);
    • gestione stato globale (indirizzo, immobile, valutazione, lead, modali);
    • dashboard staff (area admin).

Sezioni principali (in ordine logico)

  • Import: importa React e gli hook (useState, useEffect, useRef, ecc.), componenti UI (form, mappa, blog, wizard lead, footer), servizi (OMI, leads, adminLeadsService, servizi AI) e librerie di animazione come gsap.
  • Stato globale (serie di chiamate a useState):
    • currentPage: stringa che rappresenta dove si trova l’utente nell’app (es. 'home', 'pre', 'address', 'property', 'valuation', 'blog', 'blog-article', 'province-landing', 'privacy', 'terms', 'cookies', 'contact', 'support', ecc.).
    • wizardStep: step interno del wizard di valutazione (es. 'landing_address', 'main_features', 'exposure_question').
    • draftAddress e selectedAddress: la prima contiene l’input in fase di compilazione, la seconda l’indirizzo definitivo usato per OMI e per l’invio al backend.
    • omiData: risultati OMI (valori min/max/avg €/mq, affidabilità, tipo fonte).
    • propertyDraft: dati dell’immobile (superficie, piano, stato, spazi esterni, ecc.).
    • wizardData: oggetto che raggruppa ulteriori risposte del wizard (per esempio wizardData.extra e wizardData.lead: profilo utente, rapporto con l’immobile, tempistiche di vendita, consensi).
    • valuationResult: risultato della valutazione (prezzo minimo/medio/massimo, €/mq).
    • contactData: dati del contatto (nome, email, telefono, note) se l’utente compila il form.
    • isValuationUnlocked e valuationId: indicano se la valutazione è stata “sbloccata” e l’ID salvato lato backend.
    • loading ed error: gestiscono stati di caricamento e messaggi di errore globali.
    • isLeadModalOpen e showContactPopup: controllano la visibilità di modali e popup.
    • isAdminDashboard, adminTab, selectedLead ecc.: governano la vista dashboard staff.
  • Effetti su titolo e meta: un useEffect osserva currentPage, selectedAddress, currentProvinceSlug e altri flag per aggiornare document.title e la meta description in base alla pagina corrente (home, valutazione, landing di provincia, privacy, termini, cookie, contatti, centro assistenza, blog e singolo articolo).
  • Parsing dell’URL iniziale: un altro useEffect usa new URL(window.location.href) per leggere pathname e parametri (es. admin, slug blog, slug provincia), calcola flag come pathIsRoot, pathIsPrivacy, pathIsTerms, pathIsCookies, pathIsPre, pathIsHome, pathIsValutazione, pathIsContact, pathIsSupport e in base a questi imposta currentPage e lo wizardStep iniziale (di solito 'landing_address'). Se è presente ?admin=ValutatoreStaff2025! abilita la modalità dashboard staff.
  • Funzioni di navigazione “pagine”: funzioni come goToHomePage, goToValuationPage, goToPrivacyPage, goToTermsPage, goToCookiesPage, goToContactPage, goToHelpCenterPage, goToFaqPage aggiornano currentPage, azzerano alcuni stati (per esempio currentBlogSlug, wizardStep), aggiornano l’URL con window.history.pushState/replaceState e fanno window.scrollTo(0, 0).
  • Funzioni specifiche del wizard:
    • Ricerca indirizzo – handleAddressSelect(enrichedAddress) riceve l’indirizzo scelto da StepByStepAddressForm, chiama il servizio OMI per avere i valori €/mq (via omiService o realOmiService), salva selectedAddress e omiData e porta l’utente allo step proprietà ('property'), aggiornando wizardStep.
    • Form proprietà – handlePropertySubmit(property) riceve i dati compilati in PropertyForm, invia una richiesta POST /api/valuation/enhanced-omi al backend, salva valuationResult, valuationId e metadati, quindi porta l’utente alla pagina di risultato ('valuation').
    • Media e AI – funzioni dedicate inviano planimetrie/foto a /api/valuation/media, richiedono analisi a /api/valuation/ai-analyze e applicano il delta sulla valutazione tramite applyMediaDeltaToValuation.
    • Lead – funzioni chiamate da LeadQualificationWizard, ContactForm e ContactFormPopup costruiscono il payload con propertyDraft, wizardData.lead, valuationResult e consensi (marketing, agenzie), inviandolo al backend tramite leadsService.
    • Navigazione interna – goBack() gestisce il ritorno agli step precedenti (es. da proprietà a indirizzo, da valutazione a proprietà) e restart() esegue un reset globale del wizard, riportando l’utente alla landing di indirizzo e azzerando stato immobile/valutazione.
  • Rendering principale: il return definisce la struttura con un contenitore principale <div className="min-h-screen ...">, una top bar con le CTA, un blocco centrale che renderizza viste diverse in base a currentPage (pre/home, wizard, blog, landing di provincia, pagine legali, dashboard staff) e il footer <MainFooter />. Quando currentPage è 'address', 'property' o 'valuation', viene renderizzato <ValuationWizardPage /> che riceve gran parte dello stato e delle funzioni come props.

Dashboard staff – panoramica funzionale

La dashboard staff (accessibile solo in ambiente di sviluppo tramite parametro ?admin=ValutatoreStaff2025! e credenziali configurate via variabili d’ambiente) è l’area riservata per analizzare i lead raccolti, i gruppi automatici di contatti e le performance delle landing di provincia.

  • Accesso:
    • lato frontend, l’URL include il parametro ?admin=... per mostrare la UI staff;
    • lato backend, gli endpoint /api/admin/* richiedono autenticazione JWT ottenuta tramite il flusso di login admin.
  • Struttura: la dashboard è organizzata in tab, gestite da adminTab in App.jsx:
    • Overview – <ContactsDashboard /> in modalità predefinita: panoramica contatti, grafici e riepilogo gruppi automatici;
    • Contatti – gestione di dettaglio dei lead con filtri avanzati;
    • Statistiche landing province – analytics sugli accessi alle landing per provincia;
    • Mappa comuni italiani – esplorazione dei lead per regione/provincia/comune e CAP, con export CSV;
    • Raggruppamento automatico – vista sui gruppi da 5 contatti per CAP, pronta per follow-up commerciale;
    • Registro trattamenti – sintesi interna del registro GDPR.

Tab “Overview” – Dashboard contatti

  • Mostra tre KPI principali:
    • Contatti totali: numero complessivo di lead presenti in users_leads;
    • Ultimi 7 giorni: lead ricevuti negli ultimi 7 giorni rispetto ad oggi;
    • Ultimo contatto: data/ora dell’ultimo lead.
  • Grafico “Andamento contatti”:
    • bar chart con i contatti per giorno negli ultimi 7 giorni;
    • usa barData calcolato da ContactsDashboard.jsx e renderizzato via react-chartjs-2/Chart.js;
    • tooltip personalizzato che mostra “Contatti: N”.
  • Box “Top CAP per numero di contatti”: evidenzia i CAP con più lead, con numero di contatti per ciascun CAP.
  • Box “Raggruppamento automatico”:
    • mostra quanti gruppi automatici da 5 contatti esistono, quanti contatti sono già “raggruppati” e la percentuale di copertura;
    • elenca i CAP con più gruppi automatici e il numero di contatti in attesa del prossimo gruppo;
    • include la call to action “Vai al dettaglio gruppi” che porta alla tab “Raggruppamento automatico”.

Tab “Contatti” – elenco lead e scheda completa

La tab Contatti usa ancora ContactsDashboard.jsx (prop mode="contactsOnly") e offre una vista completa sui lead.

  • Filtri:
    • ricerca testuale su nome, email, telefono, città, CAP;
    • filter dedicati per CAP e città;
    • filtro media: tutti, solo con media, solo con planimetria, solo con foto, solo con analisi AI.
  • Tabella lead:
    • colonne: nome, contatti, indirizzo, CAP/città, dati immobile, valutazione, data, media/AI;
    • la colonna Valutazione mostra prezzo medio e €/mq quando valuation.valutazione è presente o il totalValue nei casi legacy;
    • badge per planimetria, numero di foto e presenza analisi AI.
  • Mini-scheda laterale: quando si clicca una riga, appare a destra una scheda con:
    • dati contatto (email/telefono);
    • indirizzo immobile e anagrafica immobile (superficie, piano, stato, camere/bagni, spazi esterni);
    • riepilogo valutazione (range, prezzo medio, €/mq);
    • stato media/AI.
  • Scheda completa contatto:
    • tramite “Apri scheda completa” viene chiamato /api/admin/leads/:id per caricare step del wizard, media e analisi AI;
    • la scheda completa mostra:
      • tutti i dati di contatto e indirizzo;
      • dettaglio immobile (superficie, piano, ascensore, camere, bagni, spazi esterni, box/posti auto);
      • profilo e intenzioni (tipo profilo, proprietà, tempistiche vendita, volontà di contatto da agenzie, consenso marketing);
      • valutazione calcolata (range, prezzo medio, €/mq) con supporto anche per il vecchio formato aggregato;
      • lista allegati caricati (planimetrie/foto) con link diretti al download;
      • eventuali analisi AI sulle immagini, con descrizione e tag estratti.

Tab “Mappa comuni italiani” – vista Raggruppa

Implementata da ContactsGroupsDashboard.jsx (modalità predefinita), consente allo staff di esplorare tutti i comuni italiani, filtrare i lead per CAP e periodo e preparare liste CSV di contatti per attività mirate.

  • Albero regioni/province/comuni: dati da gi_comuni_cap.json e raggruppamento effettuato sul frontend;
  • Filtri: selezione regione → provincia → comune, filtro per CAP specifico e per intervallo di date;
  • Nuovi contatti: indicatori e badge “Nuovi contatti” in base all’ultimo accesso, con possibilità di segnare come letti globalmente, per comune o per CAP;
  • Tabella contatti del comune: simile alla lista lead ma focalizzata sul comune selezionato, con selezione multipla per export;
  • Export CSV: pulsante “Esporta selezionati” che genera un file CSV con: dati di contatto, indirizzo, caratteristiche immobile, esposizione, URL planimetrie/foto, profilo e intenzioni e prezzo di valutazione;
  • Scheda completa da Raggruppa: per ogni riga è disponibile il bottone “Scheda completa” che apre l’overlay con gli stessi dati della scheda completa della tab Contatti, inclusi: valutazione, allegati, analisi AI e metadati OMI (semestre, tipologia, zone e fallback);
  • Export singolo contatto: dalla scheda completa è possibile scaricare un CSV dedicato al singolo lead (“Esporta contatto”).

Tab “Raggruppamento automatico”

La modalità mode="autoGrouping" di ContactsGroupsDashboard.jsx crea gruppi automatici di 5 contatti con lo stesso CAP per regione/provincia/comune, pensati per iniziative commerciali sul territorio.

  • Per ciascun gruppo sono visibili: regione, provincia, comune, CAP, numero del gruppo e data dell’ultimo contatto nel gruppo;
  • i gruppi sono marcati come “nuovi” in base a un timestamp salvato in localStorage, con possibilità di segnarli come letti;
  • per ogni gruppo è possibile espandere la lista contatti e esportare l’intero gruppo in CSV (“Esporta gruppo”).

Tab “Statistiche landing province”

Anche questa tab è realizzata da ContactsDashboard.jsx (mode="analytics") e lavora sui dati della tabella province_analytics del backend.

  • Filtri:
    • intervallo temporale (ultimi 7/30/90 giorni);
    • granularità dei bucket (giorno, settimana, mese);
    • filtro testuale per province_slug.
  • Grafico “Andamento visite”: bar chart delle visite aggregate per intervallo selezionato, calcolato da analyticsSeriesData;
  • Lista “Visite per provincia”: elenco delle province con, per ciascuna: visualizzazioni pagina, sessioni, utenti unici e durata media della sessione.

Tab “Registro trattamenti”

Tab statica che descrive in forma sintetica il registro dei trattamenti legato al valutatore (finalità, categorie di dati, interessati, base giuridica, tempi di conservazione). È pensata come supporto operativo al registro formale ai sensi dell’art. 30 GDPR.

Come usare la dashboard nella pratica

Scenario: trovare tutti i lead nuovi su un CAP e prepararne l’export per un’agenzia

  1. Accedi alla dashboard admin: apri l’app con il parametro ?admin=..., effettua il login e vai alla tab Mappa comuni italiani.
  2. Scegli area geografica: seleziona regione, provincia e poi il comune di interesse dall’albero.
  3. Filtra per CAP: nella sezione contatti del comune, imposta il filtro CAP con il valore desiderato (es. 00100). Puoi opzionalmente impostare un intervallo di date per considerare solo i lead recenti (es. ultimi 7/30 giorni).
  4. Isola i lead “nuovi”: usa i badge di “nuovi contatti” (calcolati rispetto al timestamp memorizzato) per capire quali lead non sono ancora stati visti. Se vuoi ripartire da zero, utilizza le azioni “segna come letti” globali, per comune o per CAP.
  5. Seleziona i lead per l’agenzia: nella tabella dei contatti filtrati, seleziona tutte le righe rilevanti per il CAP (puoi fare “seleziona tutto” o una selezione manuale).
  6. Esporta in CSV: premi “Esporta selezionati”: verrà generato un CSV con i campi utili per l’agenzia (dati di contatto, indirizzo, caratteristiche immobile, media, profilo, intenzioni, prezzo di valutazione). Il file può essere aperto direttamente in Excel o importato in un CRM.
  7. Approfondisci singoli lead se necessario: per i contatti più interessanti, fai clic su “Scheda completa” per consultare i dettagli, verificare planimetrie/foto, leggere la valutazione e vedere i metadati OMI e la sintesi AI prima di inoltrarli all’agenzia.

Servizi frontend – OMI & geocoding

  • realOmiService.js: database sintetico di CAP/prefissi italiani e logica di inferenza regionale per generare min/avg/max €/mq.
  • omiService.js: wrapper che usa getRealOmiValues e fallback forzati per non fallire mai, producendo sempre valori.
  • enhancedAddressService.js: combina:
    • database locale di vie principali per varie città;
    • API pubbliche Nominatim (OpenStreetMap) e Photon;
    • meccanismo di deduplica e rank per suggerimenti;
    • reverse geocoding per ricavare CAP e info OMI (regione, comune, zona).
Dettagli del motore di valutazione
Come vengono usati i dati OMI ufficiali e sintetici per calcolare il prezzo.

1. Dati in ingresso

  • Indirizzo: oggetto con almeno postcode, city, state, lat, lon, ottenuto da autocomplete e arricchimento CAP.
  • Proprietà: superficie principale, superfici accessorie (balcone, terrazzo, giardino, ecc.), piano, ascensore, stato, tipologia.

2. Fase precalcolo OMI sintetico lato FE

Quando l’utente seleziona un indirizzo, il frontend recupera subito un set di valori OMI sintetici via getOmiValues. Questi servono come base di fallback se il backend non è disponibile o se si vuole fare un calcolo locale.

3. Valutazione principale lato backend

  • Il frontend chiama /api/valuation/enhanced-omi con { address, property }.
  • Il backend decide se usare modalità strict o meno:
    • OFFICIAL_MODE_STRICT (env) e parametri query officialModeStrict/forceOfficial.
  • Viene chiamata buildCapBasedValuation(address, property, { fallbackMode, strictMode }).

4. Uso OMI ufficiale

  • Lookup comune a partire dal CAP (`findComuniByCap`).
  • Se più comuni condividono lo stesso CAP, il codice cerca di disambiguare usando city e province.
  • Recupero semestre OMI più recente (attivo, altrimenti l’ultimo presente).
  • Calcolo range comunale MIN/MAX €/mq per la tipologia corrispondente alla proprietà.
  • Caso positivo:
    • prezzoAlMetroQuadro = media tra min e max comunale.
    • Prezzo minimo/medio/massimo = min/avg/max * superficie.
    • omiData.reliability = 'UFFICIALE_COMUNALE'.

5. Fallback sintetico

Se non esiste un range OMI ufficiale valido o se la lettura del DB fallisce, il codice passa a un fallback sintetico (a meno che non sia in modalità strict).

  • Chiama getRealOmiValues(cap):
    • prima cerca un match 5-cifre nel database CAP interno,
    • poi prefisso 3-cifre, poi 2-cifre,
    • altrimenti calcola prezzi in base a regione e zona dedotte.
  • Calcola prezzoAlMetroQuadro = avg sintetico e applica uno spread ±15% per min/max.
  • Indica la natura sintetica in metadati.metodologia e metadati.fonti.

6. Aggiustamento in base ai media

Se l’utente carica una planimetria e/o foto, il backend calcola un piccolo punteggio di confidenza (conditionScore) e il frontend lo usa per spostare il prezzo finale entro un range ±8%.

  • Più foto e una planimetria aumentano leggermente il prezzo.
  • Pochi o nessun media tendono a ridurlo entro i limiti configurati.

Runbook operativo
Cosa controllare in caso di problemi con login admin, OMI o autocomplete.

1. L’app non si apre in Docker

  • Controllare lo stato dei container: 
    docker ps
  • Verificare log frontend (Nginx): 
    docker compose logs frontend
  • Se il frontend segnala problemi di backend:
    • controllare che il servizio backend sia in stato healthy (healthcheck su /health).

2. Login admin fallisce (500 o errori CORS)

  • Verificare variabili backend:
    • ADMIN_USER impostato;
    • ADMIN_PASS_HASH o ADMIN_PASS configurati.
  • Verificare ADMIN_ALLOWED_ORIGINS include l’origin del browser (es: http://localhost).
  • Controllare log backend: 
    docker compose logs backend

3. Valutazione sempre “sintetica” (nessun dato OMI ufficiale)

  • Verificare percorso OMI_DB_PATH e presenza del file omi_official.sqlite.
  • Se necessario, rieseguire lo script di import OMI (dedotto da npm run import:omi).
  • Controllare log per errori SQLITE_CANTOPEN o similari.

4. Autocomplete non propone risultati

  • Controllare console del browser per messaggi: Nominatim API fallita, Photon API fallita.
  • Verificare che la macchina abbia accesso HTTP verso internet (Nominatim, Photon).

5. Miglioramenti raccomandati (priorità)

  • Trasparenza sulla fonte dati: rendere sempre evidente all’utente se il dato è OMI ufficiale o sintetico.
  • Sicurezza admin: usare solo ADMIN_PASS_HASH in produzione; rimuovere la dipendenza da password in chiaro.
  • Indici DB: aggiungere indici su colonne usate nei filtri (es. created_at, cap, province_slug, event_type).
  • Refactoring App.jsx: suddividerlo in container specifici (wizard, admin, blog) e introdurre test.
  • Test automatici: almeno per endpoint chiave di valutazione e login admin.
